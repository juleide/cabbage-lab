# 电子皮肤 64 × 64 USB 采集卡通信协议

适用范围：64 × 64 阵列 USB 采集卡。依据《电子皮肤64X64通道采集卡通信说明.doc》和《上位机GUI软件使用说明(1).pdf》整理；连接与授权要求依具体板卡版本确认，字段推导及解析规则尚未通过实机验证。

## 1. 物理层与设备连接配置

| 项目 | 配置与要求 |
| --- | --- |
| 通信接口 | USB 2.0，USB 5 V 供电；通过厂家 SDK 或 USB 驱动库建立通信 |
| Windows 驱动 | 厂家说明要求为对应 EZ-USB 设备配置 WinUSB 驱动；替换前须确认目标设备，不对其他 USB 设备操作 |
| 设备访问参数 | VID / PID、接口、端点及传输类型未提供；不能仅凭 USB 2.0 推断为虚拟串口、HID 或 Bulk |
| 多设备区分 | 厂家软件通过 REV 区分，通常为 0、1、2、3；同一电脑上的多卡避免使用相同 REV。REV 不等同于唯一序列号，读取与选择方式待 SDK 确认 |
| 上电时序 | 依版本需在上电后等待 5～30 秒再连接或启动采集，否则可能导致厂家软件退出或连接失败；实际就绪时间需确认，不设置无依据的统一等待值 |
| 授权验证 | 部分版本需匹配的 `key.txt`，缺失或不匹配可能导致运行一段时间后停止；自研程序须确认授权文件格式、验证流程及 SDK 接口，不能直接照搬厂家软件的文件读取方式 |

## 2. 下行控制协议（Host → Device）

现有资料未提供启动、停止、握手或参数配置的具体指令字节序列，也未明确设备是否在上电后自动连续上报。官方 GUI 的“开始 / 停止”属于软件内部操作，不能据此推定存在同名硬件命令。

补齐方式：

- 向厂家索要 SDK、USB 通信指令集及调用示例，确认设备打开、授权、启动、停止和关闭的顺序。
- 使用 Wireshark + USBPcap 抓取官方软件连接、点击“开始 / 停止”及断开时的 USB 报文，区分控制传输、数据端点读写与软件本地行为。

指令未确认前，不编造或向设备发送猜测的控制报文。

## 3. 上行数据帧协议（Device → Host）

设备以行为单位上报，每个应用层数据包包含一行 64 个点，一帧包含 64 行，共 4096 个点。USB 单次读取不一定对应一个完整行包，程序应支持半包、多包合并及连续数据流解析。

### 3.1 数据包结构

以下为零起始字节偏移，按原文字段顺序推导。

| 偏移 | 字段 | 字节数 | 定义与取值 |
| --- | --- | --- | --- |
| 0～2 | 包头 | 3 | 固定为 `0xAA 0x10 0x33` |
| 3 | 包长度 | 1 | 包含包头、数据和校验的总长度；按字段推导为 `0x88`（136 字节），待抓包核对 |
| 4 | 帧号 | 1 | 范围 0～255，一帧包含 64 行 |
| 5 | 行号 | 1 | 范围 0～63 |
| 6～133 | 像素数据 | 128 | 64 个像素点的原始电压数据，每点 2 字节，按第 4 节解析与重排 |
| 134～135 | CRC | 2 | 原文称“包头、数据都参与校验”；算法、精确覆盖范围及结果字节序待厂家确认 |

```text
行包长度 = 3 + 1 + 1 + 1 + 128 + 2 = 136 字节 = 0x88
一帧像素数据 = 64 × 64 × 2 = 8192 字节
一帧行包总量 = 64 × 136 = 8704 字节（不含可能的 USB 额外封装）
```

结构示意（不是可通过 CRC 的完整报文）：

```text
AA 10 33 88 FRAME ROW [128 字节像素数据] CRC_0 CRC_1
```

不能因校验字段占 2 字节就默认使用 CRC16-Modbus，也不能自行认定长度、帧号和行号是否参与校验。CRC 未确认时只能进行结构解析，不得标记为“CRC 校验通过”。

## 4. 像素数据解析规则

### 4.1 字节序与符号位

每点占 16 bit，采用大端字节序，高 8 位在前、低 8 位在后。传输下标为 `i` 的点，其高、低字节分别位于行包偏移 `6 + 2 * i`、`7 + 2 * i`。

```c
uint16_t rawWord = ((uint16_t)highByte << 8) | lowByte;
```

原文声明最高位 `0x8000` 为符号位，但未明确负数编码方式。应先保留原始 `uint16_t`，在负数编码与换算公式确认后再转换；不得直接假定为补码并转成 `int16_t`。

电压比例、有效范围、异常值以及压力 / 力标定关系均未提供，未经换算的数据不得标注为 V、mV、N、Pa 或 kPa。

### 4.2 行内数据重排

64 个点并非按第 1～64 列依次传输，而是按步长 8 交织排列：

| 传输下标（零起始） | 对应像素点编号（从 1 开始） |
| --- | --- |
| 0～7 | 1、9、17、25、33、41、49、57 |
| 8～15 | 2、10、18、26、34、42、50、58 |
| 16～23 | 3、11、19、27、35、43、51、59 |
| 后续分组 | 按相同规律排列 |
| 63 | 64 |

按原文示例归纳的正向映射：

```text
// i、row、column 均为零起始下标，范围 0～63
column = (i % 8) * 8 + floor(i / 8)
matrix[row][column] = received_data[i]
```

反向索引：

```text
i = (column % 8) * 8 + floor(column / 8)
```

示例：`i=0` 放入第 0 列；`i=1` 放入第 8 列（原文第 9 点）；`i=8` 放入第 1 列（原文第 2 点）。该映射覆盖全部 64 列且无重复，仍需通过已知受压位置验证。重排不定义实物行列朝向、镜像或安装旋转。

## 5. 帧重组与异常处理

以下为接收端实现建议，不代表厂家已规定全部时序。

1. **查找包头**：在接收缓冲区中检索 `AA 10 33`。数据不足一个行包时保留残包等待后续读取；完整候选包内出现相同字节序列时，不因此截断数据。
2. **校验行包**：检查总长度、长度字段及行号范围，并在 CRC 规则确认后执行校验。候选包无效时继续搜索后续包头重新同步。
3. **解析并填入矩阵**：按大端读取 64 个 `rawWord`，完成步长 8 重排，写入当前帧对应行。
4. **维护行位图**：按设备、连接会话和帧周期隔离组帧状态，维护 64 行接收位图。重复行不得增加已收行数；乱序行按行号归位，重复行取舍需制定明确策略。
5. **判定完整帧**：仅当同一帧周期的行号 0～63 全部收齐并通过已实现的校验，才输出完整矩阵；CRC 未确认时须保留“未校验”状态。
6. **处理异常**：结合接收时间设置组帧超时，丢弃缺行或过期帧。帧号仅 8 位，需处理 `255 → 0` 回绕，不能只用帧号作为长期唯一标识；重连时清空残包与未完成帧，严禁使用旧帧数据填补缺行。帧率未提供，超时阈值待实测确定。
7. **保存原始数据**：建议保存原始 `rawWord`、设备标识、帧号、行号、校验状态及接收时间戳，处理结果另存。接收时间不等同于设备采样时间。厂家 Qt 软件的 `.db` / `.csv` 保存的是置零、滤波、标定之前的阵列数据，不据此推定其他软件版本的导出行为。
